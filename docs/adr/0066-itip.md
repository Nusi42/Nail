# ADR 0066: iTIP / iMIP in `nail-itip` (WP81)

Status: accepted · 2026-10-01 · M3b WP81 (parallel package; the integrator
renumbers)

## Context

WP80 (ADR 0065) fixed the scheduling contract (`nail_api::scheduling`:
methods, the invitation card, targets, issues, settings, free/busy) and
left `crates/nail-itip` as a stub. WP81 fills it: iTIP (RFC 5546)
processing for `PUBLISH`, `REQUEST`, `REPLY`, `ADD`, `CANCEL`, `REFRESH`,
`COUNTER`, `DECLINECOUNTER`; iMIP (RFC 6047) parsing and building;
organizer / attendee logic from the user's identities; `SEQUENCE` /
`DTSTAMP` ordering; recurrence-instance replies; delegation basics;
conflicts; and when CalDAV auto-scheduling (RFC 6638) means Nail must not
mail. WP85 wires it into the core.

## Decisions

### Shape: pure logic over the contract types

`nail-itip` does no I/O and owns no state. Every function takes the
contract's types (`CalendarEvent`, `EventInstance`, `BusyPeriod`, …), the
stored iCalendar text and the user's addresses, and returns contract
types, iCalendar text or MIME bytes. The core keeps reading the store,
writing through the PIM queue / outbox and recording `itip_state`,
`itip_messages`, `itip_sent`. Modules: `object` (reading), `address`,
`order`, `card`, `apply`, `build`, `imip`, `texts`, `conflicts`,
`server`.

`nail-ical` is used read-only (no changes were needed): event fields,
zones and recurrence come from its parser; occurrence edits from
`nail_ical::edit`; expansion from `nail_ical::expand`; `VTIMEZONE`
generation from `nail_ical::tz::vtimezone_for`; writing the user's copy
stays `nail_ical::write::write_event` (in the core), which patches the
stored text and keeps `SCHEDULE-AGENT` and other unknown parameters.

### Reading iTIP data (`object`)

- **Method**: the `METHOD` property wins over the MIME `method`
  parameter (they must match per RFC 6047 §2.4; calendars act on the
  data). A present but unknown `METHOD` is `unknown-method` even when
  the parameter is known.
- **One event per object**: the first `VEVENT`'s `UID`; other UIDs raise
  `several-events` and are ignored. At most 256 components and 4 MiB.
- Each component is read on its own (wrapped with the message's
  `VTIMEZONE`s and parsed by `nail-ical`), so a lone occurrence keeps its
  own fields and `RECURRENCE-ID` (which `ParsedEvent` drops for orphan
  overrides). The scheduling properties the event model leaves out are
  read here: `DTSTAMP` (RFC 3339 UTC), `SEQUENCE`, `COMMENT`, `SENT-BY`,
  `SCHEDULE-AGENT`, `X-MICROSOFT-DISALLOW-COUNTER`. Addresses are
  compared normalized (`mailto:` stripped, ASCII lowercase).
- `ADD` components carry no `RECURRENCE-ID` (RFC 5546 §3.2.4): each one's
  `DTSTART` becomes its recurrence id.
- Message-level issues: `unparsable`, `unknown-method`, `no-event`,
  `missing-uid` (fatal), `several-events`, `missing-organizer` (every
  method but `PUBLISH`), `attendee-count` — `REPLY` / `REFRESH` exactly
  one attendee **except** that a delegation reply may list the delegates
  (`DELEGATED-FROM` the replier, RFC 5546 §4.2.5); `COUNTER` at least one
  (Outlook lists everyone; the proposer is the attendee matching the
  sender — if none matches, `attendee-count`).
- The stored text of a new event is the `VCALENDAR` without `METHOD`
  (RFC 6638 §3.2), with only the event's components and the zones.

### Roles and sender checks (`card`)

- **Role**: organizer when one of the user's addresses is `ORGANIZER`;
  attendee when one is an `ATTENDEE` (the address with the best rank in
  `UserAddresses` wins — the core lists the identity of the receiving
  account first); otherwise observer. A forwarded `REQUEST` gives the
  observer the first identity, so answering adds the user ("party
  crashing", RFC 5546 §2.1.5); `not-addressed-to-me` warns.
- **Spoofing**: organizer methods must come from the organizer or its
  `SENT-BY`; attendee methods from the named attendee or its `SENT-BY`.
  The core passes `From` **and** `Sender` (Google sends with
  `Sender: calendar-notification@google.com` and the organizer in
  `From`). A mismatch adds `sender-not-organizer` /
  `sender-not-attendee`; the card still offers its actions, the core must
  never apply such a message automatically (ADR 0065).

### Ordering (`order`)

- `Version {sequence, dtstamp}`: higher `SEQUENCE` wins, then later
  `DTSTAMP`; a missing `DTSTAMP` is never newer — the same rule as the
  store's `itip_is_newer`, so card and stored state agree. Stamps compare
  as instants.
- `REQUEST` / `PUBLISH` / `ADD`: newer than the stored copy = `update`,
  equal = `current`, older = `outdated` (ignored; the card offers
  `refresh`). `CANCEL` with an **equal** version still applies (several
  producers cancel without raising `SEQUENCE`); older is `outdated`.
  `REPLY` / `COUNTER` answering an older `SEQUENCE` than the copy, or not
  newer than the last reply applied from that attendee, are `outdated`.
- Organizer side: a change is significant (bump `SEQUENCE`, reset every
  other attendee to `NEEDS-ACTION` + `RSVP`) when start / end (as
  instants), location, the recurrence, cancellation or an override's
  time changes (`order::prepare_update`).

### Applying (`apply`)

- The user's alarms and colour survive the organizer's updates (they are
  personal); everything else follows the message.
- Occurrence-only `REQUEST`s become overrides; a recurrence id the series
  does not generate is added as `RDATE` (as `ADD` does). A single event
  that gains occurrences recurs by `RDATE`s.
- `CANCEL`: no recurrence id = delete; an occurrence = `EXDATE`;
  `RANGE=THISANDFUTURE` = end the series before it (from the first
  occurrence = delete); a `CANCEL` that lists attendees without the user
  changes nothing.
- `REPLY` per occurrence creates the override from the master (start =
  recurrence id, same length) and sets the status there. A series reply
  also updates overrides whose status equalled the series' old status;
  occurrences answered on their own keep their answer. An unknown
  replier is added; delegation sets `DELEGATED` / `DELEGATED-TO` and adds
  the delegate with `DELEGATED-FROM` and `RSVP`.
- Accepting a `COUNTER` moves the series or occurrence and applies the
  significant-change rules (everyone, the proposer included, is asked
  again — the organizer's new `REQUEST` is a new version).

### Building (`build`)

| Method | Content |
| --- | --- |
| `REQUEST` / `PUBLISH` / `ADD` | the stored components (or one override), no `VALARM`, `SEQUENCE` / `DTSTAMP` set |
| `CANCEL` | meeting / occurrence / removed attendees, `STATUS:CANCELLED`, `COMMENT` |
| `REPLY` | `UID`, `DTSTAMP`, the source's `SEQUENCE`, `RECURRENCE-ID`, times (when the occurrence has an override), `SUMMARY`, `ORGANIZER`, the one attendee (+ delegates), `COMMENT` |
| `COUNTER` | the received component with the proposed `DTSTART` / `DTEND` / `LOCATION` and `COMMENT` (an occurrence drops `RRULE` / `RDATE` / `EXDATE`) |
| `REFRESH` / `DECLINECOUNTER` | `UID`, `DTSTAMP`, (`SEQUENCE`), `RECURRENCE-ID`, `ORGANIZER`, the attendee, `COMMENT` |
| delegated `REQUEST` | the received event with the delegator `DELEGATED` and the delegate added |

The attendee's original `ATTENDEE` line is reused (its `CN`, `ROLE`,
vendor parameters) with the new `PARTSTAT`. `SCHEDULE-AGENT`,
`SCHEDULE-STATUS` and `SCHEDULE-FORCE-SEND` never leave in iTIP mail.
`VTIMEZONE`s: the source's own definition for a `TZID` (keeps Outlook's
Windows names), else one generated for IANA names. A `RECURRENCE-ID` for
an occurrence without an override is written like the master's
`DTSTART` (same `TZID` spelling, value type), so every receiver matches
it. Forwarding (RFC 5546 §2.1.5) sends the received text unchanged.

### iMIP (`imip`, `texts`)

- **Finding the calendar data**: `text/calendar` with `method` (inline
  before attached), then without `method`, then `application/ics`, then
  `application/octet-stream` named `*.ics`. Parts inside attached
  messages (`message/rfc822`) are not looked at — a forwarded mail is
  not an invitation. Non-UTF-8 attachments are decoded by their
  `charset`. 32 MiB limit.
- **Sending**: `multipart/mixed` { `multipart/alternative` { `text/plain`,
  `text/html`, `text/calendar; method=…; charset=utf-8` }, `invite.ics`
  attachment } — the calendar part inside the alternative is what RFC
  6047 and Outlook / Google / Apple read; the attachment (as Google sends
  it) helps clients that only show attachments; it is optional
  (`attach_ics`, default on). `Content-Class:
  urn:content-classes:calendarmessage` lets Outlook file it as a meeting
  message. `In-Reply-To` / `References` thread an answer with the
  invitation. `OutgoingImip::body()` gives the MIME tree alone for a
  transport that writes its own headers.
- **Texts** come from a **new catalog `locales/en/itip.ftl`** (German
  twin empty) through a `Localizer` trait (closures implement it; the
  core passes `nail_config::l10n::Catalog::render` for the identity's /
  UI language). Times are numeric (`2026-10-05 09:00 – 10:00
  (Europe/Berlin)`) and wrapped by Fluent patterns; localized date
  formatting needs an ICU-style formatter that Nail does not have yet.

### Conflicts (`conflicts`)

The invited occurrences in a window (92 days from the first invited
time, but not more than a day in the past; at most 50 occurrences) are
compared with the user's instances (from the instance cache) and,
for proposals, with free/busy periods. Free (`TRANSP:TRANSPARENT`) and
cancelled instances and the invitation's own event never conflict;
tentative instances are marked tentative; at most 50 conflicts; touching
is no overlap; zero-length events conflict when they fall inside.

### RFC 6638: when Nail must not send iMIP (`server`)

The server schedules for a calendar when its source advertises
`calendar-auto-schedule` **and** the calendar is writable. Then, per
calendar user:

- organizer → attendee (`REQUEST`, `CANCEL`, `ADD`): the attendee's
  `SCHEDULE-AGENT` in the organizer's copy — `SERVER` / absent / unknown
  value = the server delivers, Nail sends **no** mail; `CLIENT` = Nail
  mails that attendee; `NONE` = nobody;
- attendee → organizer (`REPLY`): the organizer's `SCHEDULE-AGENT` in the
  attendee's copy, same values.

`COUNTER`, `REFRESH`, `DECLINECOUNTER` and forwarding have no implicit
equivalent and always go as iMIP. Without auto-scheduling everything is
iMIP. When Nail mails itself on such a calendar (a user override), it
first marks the party `SCHEDULE-AGENT=CLIENT` in the stored copy
(`mark_client_scheduled`) so the server stays out. The plan per recipient
(`DeliveryPlan`) gives the card's / result's `SchedulingTransport`:
`imip` if Nail mails anyone, else `server`, else `none`.

## Deviations from the WP80 stub sketch

- The mail texts live in the new `itip.ftl` (the orchestrator assigned
  WP81 this file), not in `core-scheduling.ftl`; the `itip-issue-*` /
  `freebusy-issue-*` ids stay where the contract put them.
- The outgoing mail is `multipart/mixed` with the calendar part inside
  `multipart/alternative` (not a top-level `text/calendar` next to the
  text), matching Google and Outlook.
- `nail-ical` needed no changes.

## Consequences

- WP85 calls `find_itip` on arrival, `parse_itip` + `card::build_card`
  for `MessageBody.invitation` (with the stored copy, the stored
  `DTSTAMP` from `itip_state`, conflicts from `conflicts::*` and the
  transport from `server::*`), `apply::*` for automatic processing (never
  with spoofing issues) and `ApplyInvitation`, `build::*` + `texts::compose` +
  `OutgoingImip` for every answer / organizer message, and records the
  versions in the store.
- `itip.ftl` must be embedded in `nail-config`'s `EN_FILES` / `DE_FILES`
  (the test `every_catalog_file_is_embedded` fails until then).
- Known limits: dates are not localized; only `VEVENT` scheduling;
  `ADD` is applied but not built; delegation covers the basics (one
  delegate, no chains or `DELEGATED-*` validation); `COUNTER` /
  `DECLINECOUNTER` to and from servers that schedule are mailed.
