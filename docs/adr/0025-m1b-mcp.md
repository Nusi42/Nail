# ADR 0025: Read-only MCP server, stdio bridge, grants and audit

Status: accepted · 2026-09-29 · M1b WP23

## Context

Plan WP23 and design.md ("MCP server") ask for a read-only MCP server on
`rmcp`: Streamable HTTP on 127.0.0.1 with per-client bearer tokens, the
design's resources and read tools, resource subscriptions for new mail and
the UI context, grants (no access until granted; per-account scope; separate
grants for raw source, attachments, encrypted content and the UI context),
an audit log, message content marked as untrusted, a `nail mcp --client
<name>` stdio bridge, and the settings UI. ADR 0022 fixed the protocol
(`nail_api::mcp`) and the store tables (clients with token hashes, grants,
audit). WP23 may not edit the core, the store or the API (integrator-owned
in M1b), so everything lives in `crates/nail-mcp`, `crates/nail-cli` and
`ui/src/features/mcp`, with small, listed hooks for the integrator.

## Decisions

### Crate shape: a data trait, the store for clients

- `nail-mcp` reads user data only through the **`McpData` trait**
  (accounts, virtual accounts, folders, folder pages, message summary /
  body / raw / attachment / encrypted flag, thread, search, rules text, UI
  context, draft, `emit(Event)`). It uses native `async fn` in traits
  (`impl Future + Send`), no `async-trait`. Tests use fakes.
- For the core, `nail-mcp` ships **`CoreData<C: CoreAccess>`**, an
  `McpData` built on four things the core already has: `handle(Request) ->
  Response` (`Service::handle`), the `Store`, the `BlobStore` and an event
  emitter. Reads go through the same requests as the UI (`ListAccounts`,
  `GetMessage`, `Search`, `GetThread`, `ListRules` + `RuleToText`,
  `GetUiContext`, `GetDraft`, …). Message summaries come from
  `Store::get_message`; raw sources from the blob store (a headers-only
  message is fetched once through `GetMessage`); attachments are cut out of
  the raw source with `nail_mime::attachment_content`. "Encrypted" means a
  top-level `multipart/encrypted` or `application/(x-)pkcs7-mime` content
  type (Nail does not decrypt before M2, so the grant guards ciphertext
  today and decrypted content later).
- Clients, grants and the audit log are read and written with the
  `nail-store` API directly (`mcp_client_by_token`, `get_mcp_client`,
  `append_mcp_audit`, `touch_mcp_client`, …); `nail_mcp::admin::handle`
  answers the six Client API requests (`ListMcpClients`, `CreateMcpClient`,
  `UpdateMcpGrants`, `RevokeMcpClient`, `ListMcpAudit`,
  `GetMcpServerInfo`) and emits `McpClientsChanged` after each change.
- Tokens: `nail_mcp_` + 32 random bytes (OS randomness via `getrandom`),
  base64url. Only the SHA-256 (`hash_mcp_token`) and the last 4 characters
  (hint) are stored. Client names are 1–64 characters, unique among active
  clients.

### Transport and authentication

- `McpServer::start` binds **127.0.0.1** only (port configurable, 0 =
  any), mounts rmcp's `StreamableHttpService` at `/mcp` with a
  `LocalSessionManager`, and sets `enforce_origin_validation()` (any
  browser `Origin` is refused; rmcp's default `Host` check against
  localhost stays). Both legacy sessions (protocol ≤ 2025-11-25) and
  stateless 2026-07-28 requests are served.
- An axum middleware authenticates **every HTTP request**: `Authorization:
  Bearer <token>` → SHA-256 → active client. Unknown / missing / revoked
  tokens get `401` with `WWW-Authenticate: Bearer` and an audit entry of
  kind `connect`, outcome `denied`, no client. The client is passed to the
  handler in the request extensions (rmcp copies the HTTP request parts
  into each MCP request's extensions). Since the token is checked per
  request, **revocation takes effect on the next request** of an open
  session.
- `/whoami` returns the token's client id and name (used by the bridge).
- The server writes **`mcp-endpoint.json`** (`{url, pid}`, no secret) into
  the data directory when it starts and removes it when it stops (only if
  it still names its own URL).

### Grants

- A grant is resolved per call from the store (`Access`): an empty grant
  (no scope, or no account and not "all accounts") allows nothing. A
  virtual account in `accounts` grants its member accounts; the built-in
  `all` equals "all accounts". Excluded folders are hidden everywhere.
- Scopes: `read` for everything; `raw-source` for `…/raw`, `attachments`
  for `…/attachments/{n}`, `encrypted` for any content of an encrypted
  message, `context` for `nail://ui/context` / `get_ui_context`. The write
  scopes of ADR 0022 are not used before M4.
- Lists (folders, folder pages, search hits, threads) are filtered to what
  the grant allows. *Changed by ADR 0028:* a restricted search pages over
  the readable hits only, with no `hidden` count and no total; threads have
  no `hidden` count and a restricted grant gets subject / participants of
  the visible messages.
- `nail://rules` (and the rules in listings) need a grant for **all
  accounts**, because rules name addresses and folders of every account.
- The UI context shows the open message only if the grant allows reading
  it; otherwise only `{id, hidden: true}`. Selected message ids are
  filtered the same way; the open draft, account, folder and thread too
  (ADR 0028). Every successful context read emits
  `McpContextAccess` (the UI's indicator).
- A refused resource read or subscription is a JSON-RPC error
  (`invalid_request`, `data: {"nail": "denied", "reason": …}`); a refused
  tool call is a tool error result (`{"error": "denied", "detail", "hint"}`)
  so agents can show the user what to grant.

### Resources, tools, untrusted content

- Resources: `nail://accounts`, `nail://accounts/{id}/folders`,
  `nail://folders/{id}/messages[?offset=&limit=]` (**added**: a folder page,
  the natural target of "new mail" subscriptions), `nail://messages/{id}`,
  `…/raw`, `…/attachments/{n}`, `nail://threads/{id}`, `nail://rules`,
  `nail://ui/context`. Ids are opaque, so each is one percent-encoded path
  segment. JSON results carry `…_uri` links to related resources.
- Tools (all annotated read-only, idempotent, closed-world):
  `search_messages` (query language, account / folder filter, paging with
  `offset` / `next_offset`, at most 200), `get_message`, `get_thread`,
  `list_folders`, `get_ui_context`.
- **Untrusted content.** Everything that comes from the mailbox (messages,
  folder pages, threads, search results, UI context) is wrapped as
  `{"untrusted_content": true, "notice": …, "data": …}`; raw and
  attachment blobs carry `_meta: {"nail/untrusted_content": true}`. The
  server instructions repeat the notice. Agent-facing texts (tool
  descriptions, notice, denial reasons) are English, like developer
  diagnostics: the UI never shows them.

### Subscriptions

- Legacy `resources/subscribe` / `unsubscribe` are kept per session (the
  session's `Peer`), and 2026-07-28 `subscriptions/listen` streams per
  stream (`SubscriptionSink`). Subscribable: `nail://accounts`,
  `nail://accounts/{id}/folders`, `nail://folders/{id}/messages`,
  `nail://ui/context`; subscribing checks the grant and is audited
  (`subscribe`).
- The core feeds `McpServer::on_event(&Event)`: `NewMail` updates the
  account's `folders` and the folder's `messages`, `MailChanged` the
  folders' `messages`, `AccountsChanged` `nail://accounts`; and calls
  `McpServer::ui_context_changed()` after each `ReportUiContext`. The grant
  is checked again before every notification (revoked or narrowed clients
  stop getting them at once).

### Audit

One entry per `resources/read`, `resources/subscribe`, each URI of
`subscriptions/listen` and `tools/call`, with outcome `allowed`, `denied`
(detail = the reason) or `error` (detail = the error). Listing resources /
tools is not audited (no data is returned beyond what the grant allows).
Each authenticated request also updates the client's `last_used_at`.

### The stdio bridge: loopback HTTP with the token, not a named pipe

`nail mcp --client <name>` is a transparent pump between stdin/stdout and
the app's Streamable HTTP endpoint (rmcp's stdio server transport on one
side, its reqwest Streamable HTTP client on the other). It finds the URL in
`mcp-endpoint.json` (or `--url`), reads the token from `NAIL_MCP_TOKEN`,
checks with `/whoami` that the token belongs to `<name>` (clear errors for
a missing, wrong or revoked token and for an app that is not running) and
then forwards every JSON-RPC message; closing stdin ends it.

Why not the named pipe the design mentions:

- **Same security model for every client.** A pipe would authenticate by
  OS user, so any process of the user could claim any client name and get
  its grant. With the token, the bridge is exactly as strong as an HTTP
  client, and the app does all grant checks, auditing and subscriptions in
  one place.
- **No second protocol path.** The pipe would need its own framing and its
  own session handling; loopback HTTP reuses the tested server unchanged.
- The token is the client's secret either way; the MCP client config holds
  it in its `env`, never on the command line (process lists).

The bridge's HTTP client has no overall timeout (the notification stream
is long-lived; `nail_auth::http_client()`'s 30 s would cut it), a 5 s
connect timeout and **no proxy** (a system proxy must never see the token).

## Deviations and deferrals

- **Named pipe → loopback HTTP** (above).
- **"If the app is not running, `nail mcp` starts the core headless"**:
  deferred. `NailMcp::for_client(store, data, client_id)` already serves one
  fixed client over any transport, so a headless start is the core's
  `McpData` plus `serve((stdin, stdout))`; it needs the core and a
  single-instance lock on the data directory, which is integration work.
- **Rate limits per client**, **prompts** (`summarize_thread`, …) and
  identities / capabilities in `nail://accounts`: later (M2 / M4).
- The design's `/ui/context` "fires when the draft is edited": the UI
  reports the open draft id (saved drafts only) and not every keystroke;
  cursor position is not reported yet (`draft_cursor: null`).

## UI (features/mcp)

- Widget `mcp-clients` (settings): server state, create client → the token
  is shown once (copy, usage hint), client list with access state, grant
  editor (read scopes, all accounts or chosen accounts incl. virtual ones,
  hidden folders per account), revoke with confirmation, audit log per
  client or for all clients with paging and refresh.
- Widget `mcp-context-indicator`: a status region that says "`<client>` is
  reading what is on your screen" for 4 s after each `McpContextAccess`
  (restarted by further reads), dismissable (`mcp.indicator.dismiss`).
- Effect `UiContextReporter`: sends `ReportUiContext` (debounced 250 ms,
  only on change) with the active account, folder, message, thread, the
  text selected inside the message reader (≤ 4000 characters) and the open
  draft id.
- The mock core (`features/mcp/mock.ts`) implements the six requests with
  the core's rules and a demo client; `simulateContextRead` drives the
  indicator in tests and demos.

## Consequences

- The integrator wires: `nail-core/src/mcp.rs` → `nail_mcp::admin::handle`;
  `impl CoreAccess` for the service; starting `McpServer` (with the endpoint
  file) in `nail serve` and the desktop app; forwarding events and UI
  context reports; widget kinds in `nail-config/src/widgets/mcp.rs`; the
  default layout (settings tab, indicator in the status bar) and theme
  parts. See the WP23 report.
- Tests: `crates/nail-mcp/tests/server.rs` runs an rmcp client over real
  HTTP against the server (nothing before a grant, per-scope grants,
  audit, bad and revoked tokens, tool filtering, UI context and indicator
  event, legacy and 2026-07-28 subscriptions); `tests/bridge.rs` and
  `nail-cli/tests/mcp_bridge.rs` drive the bridge (in-process and the real
  binary); `tests/core_data.rs` covers `CoreData` with a store and blob
  store.
