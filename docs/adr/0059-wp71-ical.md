# ADR 0059: nail-ical — lossless iCalendar / vCard, Nail's own recurrence engine (WP71)

Status: accepted · 2026-10-01 · M3a WP71

## Context

WP71 fills `crates/nail-ical` (stub at the contract, ADR 0058): parse and
write iCalendar (RFC 5545, RFC 7986, RFC 9074) and vCard 2.1 / 3.0 / 4.0
**losslessly**, map them to `nail_api::pim`, expand recurrences, resolve
time zones (IANA, Windows / Outlook names, custom `VTIMEZONE`s, DST gaps
and folds), compute alarms and read ICS feeds. The contract pre-declared
calcard 0.3.14 (Apache-2.0 OR MIT) and chrono-tz.

Two facts about calcard decided the design:

* its writer re-serializes everything from its model (upper-cased
  enumerated values, `KIND:GROUP`, reordered parameters), so it cannot
  give "unchanged properties keep their original text";
* its RRULE iterator (a port of rust-rrule / python-dateutil) is
  crate-private and only reachable through `ICalendar::expand_dates` on
  calcard's own model; dateutil also deviates from RFC 5545 in two corner
  cases (below).

## Decisions

### Own content-line layer, lossless by construction (`content`)

Nail parses content lines itself: unfolding (CRLF, bare LF, tabs),
groups (`item1.EMAIL`), parameters (quoted values, RFC 6868 carets,
vCard 2.1 bare types such as `TEL;WORK;VOICE`), quoted-printable soft line
breaks, vCard 2.1 base64 continuation lines; malformed lines are reported
(`ical-malformed-line`) and skipped, unclosed components closed at the
end. **Every parsed property keeps its original physical lines** and is
written back verbatim until it is changed; changed or new properties are
written canonically and folded at 75 octets on UTF-8 boundaries. Input
bytes are decoded as UTF-8, UTF-16 (BOM) or Windows-1252; `CHARSET=` and
quoted-printable values are decoded per property (`encoding_rs`, already
in the lock; (Apache-2.0 OR MIT) AND BSD-3-Clause).

### Writers patch the stored text (`write`, `vcard`)

`write_event` / `write_task` / `write_contact` / `write_group` take the
item's stored text (`raw`) and, field by field, compare what the original
means (read with the same readers the parser uses) with the edited model:

* equal → the original properties stay byte for byte (an unchanged item
  is written back exactly; the corpus tests check every item);
* different → only that field's properties are rewritten, keeping the
  parameters Nail does not manage (`X-NUM-GUESTS`, `SCHEDULE-STATUS`,
  `LANGUAGE`, `SENT-BY`, …), the original `TZID` spelling (`W. Europe
  Standard Time`) and vCard groups / Apple labels;
* list fields (attendees, alarms, attachments, emails, phones, …) are
  matched entry by entry: identical entries stay as written, edited ones
  keep their unknown parameters (attendees by email, alarms by `UID`,
  vCard entries by value or position);
* unknown properties and components (`X-…`, `X-APPLE-STRUCTURED-LOCATION`,
  `ACTION:NONE` alarms, vendor blocks, `VJOURNAL`) are never touched;
* `DTSTAMP` / `REV` are refreshed only when something changed; a
  `DURATION` stays a `DURATION`; a changed `DESCRIPTION` drops Outlook's
  stale `X-ALT-DESC`; a changed `TRANSP` drops `X-MICROSOFT-CDO-BUSYSTATUS`;
* zones used for the first time get a `VTIMEZONE` generated from chrono-tz
  through calcard's `ICalendar::add_timezone` (the one place its writer
  is used; the generated block is re-parsed into Nail's model);
* vCard 2.1 cards are returned unchanged when unchanged and become clean
  vCard 3.0 once edited (quoted-printable and `CHARSET` decoded).

### Own recurrence engine (`recur`, `expand`, `edit`)

Nail's engine generates occurrences in the **wall-clock frame of the
series start** and turns them into instants afterwards, with RFC 5545's
rules: a time in a DST gap moves forward by the gap, an ambiguous time is
the first one. It implements the full expand / limit table (all `BY*`
parts, `BYSETPOS`, `BYWEEKNO` with `WKST` incl. weeks that start in the
previous year and negative week numbers, negative ordinals, `COUNT`,
inclusive `UNTIL` compared as an instant for zoned starts, as a date for
all-day ones), skips invalid dates (Feb 30, Feb 29 in common years) and
stops impossible rules. Deliberate RFC readings where dateutil differs:

* `DTSTART` is always the first occurrence and counts toward `COUNT`,
  even when it does not match the rule (RFC 5545 3.8.5.3);
* `BYDAY` entries are alternatives: `BYDAY=TU,1TU` is every Tuesday
  (dateutil requires both lists to match);
* `BYSETPOS` selects from the whole first period before dropping what
  lies before `DTSTART` (rust-rrule drops first).

The RFC 5545 examples (section 3.8.5.3) are unit tests, and a property
test compares the engine with calcard's iterator as an independent oracle
on random rules (thousands of cases; only the three readings above are
excluded from the comparison).

Instances (`expand::instances`) apply overrides wherever they moved their
occurrence, hide cancelled and `EXDATE`d occurrences, keep the master's
wall-clock length across DST changes, place all-day and floating events in
the viewer's zone, and support `RANGE=THISANDFUTURE` overrides.

**THISANDFUTURE**: `EventOverride` has no range flag, so the parser
reports those recurrence ids in `ParsedEvent::this_and_future` and
`ExpandOptions::this_and_future` takes them; the writer keeps the
`RANGE` parameter because the original `RECURRENCE-ID` line stays as
written. A contract field is requested from WP75 (follow-up).

Edit scopes (`edit`): `override_occurrence` / `delete_occurrence`
(`this`), `end_before` / `split_series` (`this-and-following`: the old
series ends with `UNTIL` one second / one day before the occurrence, the
new one gets the later `RDATE`s, `EXDATE`s, overrides and the remaining
`COUNT`; written with `RELATED-TO;RELTYPE=SIBLING` to the old `UID`),
`move_series` (`all`: recurrence ids, `RDATE`s, `EXDATE`s follow the
start), `advance_task` (completing a recurring task).

### Time zones (`tz`)

`TZID` resolution order: IANA name (also behind `/mozilla.org/…/` and
`/softwarestudio.org/…/` prefixes) → calcard's Windows / Outlook name table
(`W. Europe Standard Time`, `(UTC+01:00) Amsterdam, …`) → the
`VTIMEZONE`'s `X-LIC-LOCATION` / `X-MICROSOFT-CDO-TZID` → **matching the
definition's rules** against every IANA zone (same UTC offset every day
for three years around the item; a zone whose city appears in the `TZID`
wins, then common zones) → fixed offsets as `Etc/GMT±N`. Definitions
that match nothing are evaluated themselves (observances with `RRULE` /
`RDATE`, gaps and folds) and their times converted to UTC
(`ical-custom-time-zone`); unknown `TZID`s without a definition read as
floating (`ical-unknown-time-zone`).

### Mapping notes

* Times: `VALUE=DATE` → `date`, `…Z` → zoned `UTC`, `TZID` → zoned IANA,
  else floating (feeds: in `X-WR-TIMEZONE`). `DURATION` becomes an end;
  a missing end is one day (dates) or zero; ends before the start are
  fixed. `RDATE;VALUE=PERIOD` keeps only the start (the contract has no
  per-date duration).
* Conferences: RFC 7986 `CONFERENCE`, vendor properties
  (`X-GOOGLE-CONFERENCE`, `X-MICROSOFT-SKYPETEAMSMEETINGURL`, …) and
  Meet / Zoom / Teams / Webex / Jitsi links found in `LOCATION`, `URL`,
  `DESCRIPTION`, de-duplicated.
* Attachments: URLs stay links; inline `BINARY` data is decoded
  (`InlineData`, SHA-256 for the blob store; the writer gets bytes back
  through `WriteOptions::blobs`). Message links are `ATTACH:mid:`
  (RFC 2392, percent-encoded) with `FMTTYPE=message/rfc822` and the
  subject in `X-NAIL-SUBJECT`; the local message id is not written.
* Alarms: `ACTION:NONE` (RFC 9074) is not a reminder (kept in the text);
  Apple's `X-WR-ALARMUID` counts as `UID`; a `DISPLAY` alarm without text
  is written with the item's title (RFC 5545 requires one) and read back
  as "none". Alarm times: relative to start / end, absolute once per
  series, `REPEAT`, `ACKNOWLEDGED` hides earlier firings. Tasks:
  `RELATED=START` counts from `DTSTART`, `RELATED=END` from `DUE`, a task
  with only one of them uses that one.
* Tasks: `RELATED-TO` (`RELTYPE=PARENT` or none) → `parent_uid` (the
  store maps UIDs to task ids); other relations stay.
* vCard: Apple labels (`_$!<Mobile>!$_` → kind `cell`, custom text →
  `label`), `TYPE=pref` / `PREF=1`, `X-ABShowAs:COMPANY`, birthdays
  without year (`--MMDD`, `X-APPLE-OMIT-YEAR`), `X-ANNIVERSARY`,
  `X-ABRELATEDNAMES`, photos (vCard 4 `data:` URI, vCard 3 `ENCODING=b`;
  at most `MAX_CONTACT_PHOTO_BYTES`, else `vcard-invalid-photo`),
  custom fields = `X-` properties that are not vendor internals. Group
  members are compared by `uid_key` (`urn:uuid:` stripped, lower case).
  Missing `UID`s are derived from the content (`nail-<sha256>`), so
  re-importing updates instead of duplicating.
* Problems: `Issue` with Fluent ids `ical-*` / `vcard-*` in
  `locales/en/core-ical.ftl` (German file empty), turned into
  `PimImportIssue`s by `import::preview`; a test keeps catalog and code in
  step.

### Corpus and tests

`tests/corpus/` holds synthesized exports in the shapes Google,
Outlook (incl. a Windows-1252 vCard 2.1), Apple (iCloud calendar,
Reminders, Contacts with an Apple group) and Thunderbird produce, a
holiday feed and RFC edge cases (documented in its README; a nested
`.gitattributes` keeps the files byte-exact). `tests/corpus.rs` checks
their meaning, that every unchanged item is written back byte for byte,
and that an edit keeps every other original line. `tests/properties.rs`
(proptest, no regression files in the source tree) checks content-line,
RRULE, event and contact round trips, expansion invariants, instance
ranges, and the calcard oracle.

## Consequences

* calcard is used for the Windows zone table, CDO zone ids and
  `VTIMEZONE` generation (plus as a test oracle); dependencies added to
  `nail-ical`: workspace `base64`, `sha2`, `hex`, and `encoding_rs`
  (already in the lock). No new packages in `Cargo.lock`.
* WP73 / WP75 store `ParsedEvent::raw` / `ParsedContact::raw` as the
  item's text, pass it back as `original` when writing, and keep
  `this_and_future` until the contract has a field for it.
