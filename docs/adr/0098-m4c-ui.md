# ADR 0098: M4c UI — command palette, printing, import / export / backup wizards, diagnostics, recovery key, smartcards

Status: accepted · 2026-10-02 · M4c WP124

## Context

Plan section 9, WP124, against the contract of ADR 0094: the command
palette, printing and saving as PDF, the import / export / backup wizards
with progress and per-item reports and the restore dry run, the vault
recovery-key flow, the smartcard PIN dialog and settings, and the
diagnostics bundle. WP124 owns `ui/src/features/{portability,palette,print}`,
the M4c additions in `ui/src/features/security/` and their catalogs; the
core serves most of these requests only after WP125, so every request has a
realistic simulation in the feature's `mock.ts`.

## Decisions

### Command palette (`features/palette/`)

- **A dialog, not an overlay of its own**: `command-palette` opens in the
  standard modal window frame (`WindowLayer`), so focus handling, Escape
  (`window.close`), the title and theming work like every other window.
  `palette.open` toggles it; the default bindings Ctrl+K and Ctrl+Shift+P
  belong in `defaults/layout.kdl` (WP125), in the `global` **and** `window`
  contexts so the palette opens and closes from anywhere.
- **Contexts are captured when it opens** (`contextsOf`: key context, a
  selected message → `list` / `reader`, the composer, open PIM windows,
  the desktop app = `GetInstallation` succeeds) because focus moves into
  the palette.
- **Entries** come from `buildPalette` (`actions/palette.ts`) over every id
  in `appRegistry.actions` plus the layout's plug-in command aliases
  (`plugins.run-command` aliases get `source: "plugin"`) and the layout's
  own aliases. Descriptions: the features' `actionInfo` win over
  `palette/builtinInfo.ts`, which describes the built-ins and every
  feature that predates `Feature.actionInfo` (title fallback, keywords,
  availability; argument-only actions such as `window.open` and
  `mail.move-to` are hidden — the layout's aliases stand for them). A test
  fails when a registered action has neither a description nor a layout
  label.
- **Fuzzy search** (`fuzzy.ts`, pure): every typed word must match the
  title or a keyword — word start > substring > letters in order — with
  accents and case folded one character per character so matches can be
  highlighted; recent actions get a small boost; unavailable actions stay
  listed but last, dimmed, and choosing one explains where it works
  instead of running it.
- **Keyboard-first**: WAI-ARIA combobox + listbox with
  `aria-activedescendant`; ↑ ↓ (wrapping), Page Up / Down, Ctrl+Home / End,
  Enter. Running closes the palette first (focus returns to where the user
  was) and then records the action (`RecordActionUsed`).
- `Palette.tsx` imports the app registry; `index.ts` loads it with
  `React.lazy` so `features/registry.ts` and the palette never import each
  other while modules load (and the palette is its own chunk).

### Printing (`features/print/`)

- **The print view is a hash route rendered by an effect**: `PrintHost`
  (feature effect) renders `#/print/<job>` through a portal over the app;
  `PRINT_BASE_CSS` hides everything else when printing and covers the app
  on screen. No change to `App.tsx` was needed, and the desktop shell's
  hidden PDF window can load the same route.
- **"Print variant" = the `print.*` parts plus the `print` colour mode**:
  while the view is shown `<html data-nail-mode="print">` is set (restored
  afterwards). A theme's `modes.print` token set — `:root[data-nail-mode="print"]`,
  which the compiler already emits for any mode name — applies; without one
  the light base values do, so dark mode never prints light-on-dark. This
  needs no new theme syntax (ADR 0094), only nail-config accepting `print=`
  token values (apiRequest to WP125).
- **Pages**: CSS named pages (`@page a4-portrait`, … for every size and
  orientation) selected by the view's `data-page`; WebView2's `PrintToPdf`
  gets the same options from the job in the shell.
- **Mail is printed as text** (`MessageBody.text`), with quoted runs kept
  or replaced by a note, headers basic / full and the attachment list. The
  sanitized HTML is not printed in v1: it is shown only in a sandboxed,
  opaque-origin iframe whose height the UI cannot measure, and an iframe is
  cut at its box when printed. A paginated HTML print is a follow-up.
- `PrintViewReady` is sent once the job and everything it shows are loaded
  (no query fetching) and laid out (next animation frame). If this window
  asked to print, `window.print()` follows and the view closes on
  `afterprint`.
- **Save as PDF**: on the desktop `SavePrintPdf` with a path typed or
  chosen with `PickPath`; elsewhere the core's `unsupported`
  (`desktop-unavailable`) turns the dialog into "use the print dialog's PDF
  printer". `printSheet(ui, node)` prints local content without a job (the
  recovery kit).

### Import, export, backup, diagnostics (`features/portability/`)

- **Wizards are dialogs** (`import-wizard`, `export-wizard`,
  `backup-wizard`, `restore-wizard`, `diagnostics-bundle`,
  `portability-report`), opened by actions (`import.open` — the first-run
  screen's offer —, `export.open`, `backup.create`, `backup.restore`,
  `diagnostics.open`) and by the future Settings widgets `import-export`,
  `backup-restore`, `diagnostics`, which also list recent jobs.
- **Jobs live in the query cache** (`["portability","job",id]`), updated in
  place by `PortabilityJobProgress` / `PortabilityJobFinished`
  (`applyJobEvent`); no polling. `JobView` shows progress (indeterminate
  while the total is unknown) with Cancel, then the report: outcome,
  non-zero counts, every per-item issue (text from `localized`, where:
  label / file › folder / item n, the English detail behind "Details"),
  the "N more" note; wizards add their part (Thunderbird proposals, the
  manifest, the restore summary).
- **Thunderbird proposals are never applied automatically**: after the
  import the report offers the accounts (the one already in Nail
  unticked) and filters; "Add chosen accounts" sends `AddAccount` with no
  secrets (passwords are never imported), "Save chosen filters" sends
  `SaveRule` (incomplete filters disabled).
- **Restore = open → (check) → choose → dry run → confirm**:
  `InspectBackup`, optionally `VerifyBackup`, `PreviewRestore` shown as a
  table per item (replace / add what is missing / add / leave as is with
  counts and notes), problems, accounts needing passwords, restart — and
  only "Restore now" starts `StartRestore`.
- **Diagnostics show exactly what goes in**: the preview lists every file
  with size, redactions and the text preview; changing any option drops
  the preview, so the bundle is only saved after the user saw the preview
  of exactly those options. Mail items need messages picked one by one
  (the selected message is offered, never ticked).
- **Paths** (`PathField`, shared with print and security): typed, or the
  system dialog through `PickPath`; after `unsupported` the Browse buttons
  disappear and the field says to type the full path (web mode). Default
  file names built from catalog messages drop Unicode isolation marks
  (`plainText`).

### Recovery key and smartcards (`features/security/`)

- The recovery key's text form is mirrored in TypeScript
  (`recoveryKeyText.ts`: Crockford base32 + CRC-32 check characters,
  forgiving parse; a test pins the core's vector for 32 zero bytes), so
  typos are reported while typing and never sent as a wrong key.
- **Create** shows the key once (groups of four; Copy; Print through
  `printSheet`; optional recovery-kit file), requires "I have stored it",
  then asks the user to type it back (`VerifyRecoveryKey`) before it is
  done; the key lives only in the dialog's state and is dropped after the
  check. **Check**, **Remove** (with a warning) and **Restore**
  (`RestoreVaultKey`) are separate dialogs; `RecoveryGate` opens Restore
  once per session when `VaultStatus.needs_recovery`.
- **PIN prompts**: `PinRequested` queues the prompt in a per-UI store and
  opens `smartcard-pin`; each prompt gets a fresh form (the PIN is
  component state only, cleared after sending); a wrong PIN comes back as a
  new prompt with `retry`; `PinPromptClosed` shows why the core stopped
  waiting; closing the dialog answers `null` for prompts still waiting.
- **Smartcard settings** (`security-smartcards`): modules (full paths,
  enabled), PIN cache 0–480 minutes, cards with keys and certificates,
  problems per module, "Use for S/MIME / OpenPGP" (`UseSmartcardKey`).

### Mocks

`portability/mock.ts`, `print/mock.ts` and `security/vaultMock.ts`
simulate WP121 / WP122 / WP125: job phases with progress events and
reports with issues, export conflicts, encrypted backups by passphrase,
restore plans, diagnostics manifests, `PickPath` with a desktop host
(`desktop` flags; off by default like `nail serve`), PDF files, recovery
keys, tokens and PIN prompts (`simulatePinRequest`, `closePinPrompt`,
`simulateLostVaultKey`).

## Consequences

- WP125 must append `PORTABILITY_BASE_CSS`, `PALETTE_BASE_CSS` and
  `PRINT_BASE_CSS` to the compiled theme's base CSS, add `print.*`,
  `palette.*`, `wizard.*`, `portability.*`, `diagnostics.*`, `recovery*`,
  `smartcards.*`, `pin-prompt*` parts to `defaults/theme.kdl`, bind
  `palette.open`, add print actions to toolbars / menus, and place the
  five future widgets in Settings (apiRequests of WP124).
- The system feature's first-run test that expected the import placeholder
  must now expect the "Import…" button (the action exists).
- HTML mail prints as text until a paginated HTML print view exists.
