# ADR 0060: CalDAV / CardDAV client, mock server and Radicale interop (WP72)

- Status: accepted (M3a WP72)
- Context: plan section 8, WP72; contract ADR 0058; sockets ADR 0057.

## Decision

`nail-dav` is Nail's own CalDAV (RFC 4791) / CardDAV (RFC 6352) client on
the workspace `reqwest` (TLS from `nail-auth`: rustls + ring + platform
verifier) and `quick-xml`. No DAV library was added: the Rust crates found
(`libdav`, `minicaldav`, …) are either GPL/AGPL, thin, or bring their own
HTTP stack; the protocol subset Nail needs is small and testable.

### Layers

| Module | What |
| --- | --- |
| `xml` | a namespace-aware element tree on `quick_xml::NsReader` (text, CDATA, entity and character references, attributes; DOCTYPE refused; depth ≤ 64, ≤ 2 M elements); escaping for request bodies |
| `client` | `DavClient`: auth, URL policy, redirects, response limit (64 MiB), `Retry-After`, error mapping |
| `multistatus` | `207` parsing: responses, propstats (only `2xx` props count), response status, `sync-token`, `DAV:error` bodies |
| `ops` | PROPFIND, REPORT (`calendar-query` with `comp-filter` + `time-range`, `calendar-multiget`, `addressbook-query` with `text-match`, `addressbook-multiget` in batches of 50, `sync-collection` with `limit`), GET, PUT / DELETE with preconditions, MKCALENDAR, extended MKCOL (RFC 5689), PROPPATCH; collection properties |
| `discovery` | RFC 6764 candidates and principal / home-set lookup |
| `sync` | one collection: `sync-collection` → fallback ctag + ETag listing; multiget of changes |
| `write` | conditional writes with "server wins" conflicts |
| `error` | `DavError` → `ErrorCode`, retry hint, `dav-*` Fluent ids (`locales/en/core-dav.ftl`) |

### Security and URL policy

- Only `https:` URLs, or `http:` to a loopback host (`localhost`,
  `127.0.0.0/8`, `::1`; tests and local servers) — the same rule as the
  contract's `is_https_or_loopback_url`. Basic credentials therefore never
  travel in clear text to a remote host. `route_all_to(addr)` (tests,
  end-to-end runs) keeps the policy on the *logical* URL.
- Redirects are followed by the client itself (the `nail-auth` builder
  disables reqwest's) for safe methods only (`GET`, `HEAD`, `PROPFIND`,
  `REPORT`, `OPTIONS`), at most 5 hops, each hop checked against the URL
  policy, never from `https:` down to `http:`. Credentials follow
  redirects to other `https:` hosts, because `/.well-known/` commonly
  points to a different host (the domain owner chose it).
- `Authorization` header values are marked sensitive; `DavAuth`'s `Debug`
  hides passwords and tokens.

### Authentication

`DavAuth::{None, Basic, Bearer, OAuth2}`. `OAuth2` asks the core's
`AccessTokenProvider` (Google) for a token per request; after a `401` it
asks once more with `force_refresh` and retries; a second `401` is
`AuthFailed`. Token errors pass through unchanged (`DavError::Token` →
the original `EngineError`). Google endpoints: `GOOGLE_CALDAV_URL` /
`GOOGLE_CARDDAV_URL`, also tried for `gmail.com` / `googlemail.com`
domains.

### Discovery (RFC 6764)

Candidates in order: the configured URL and `/.well-known/caldav|carddav`
on its host; `_caldavs._tcp` / `_carddavs._tcp` SRV through
`nail_discovery::DnsLookup` (the OS resolver, no DNS sockets) sorted by
priority / weight, with each target's `/.well-known/` URI and root; the
email domain's `/.well-known/` URI; Google's fixed endpoints. TXT `path=`
records are not read (ADR 0058: the resolver has no TXT query); the
well-known redirect covers them. Plain `_caldav._tcp` is ignored. Per
candidate: `PROPFIND depth 0` of `current-user-principal` (or
`principal-URL`, or home sets right on the candidate, or the candidate
being a collection itself), then the principal's `calendar-home-set` /
`addressbook-home-set` (the principal itself when none), then
`PROPFIND depth 1` of each home set. A `401` stops discovery at once; a
TLS or network failure is reported rather than "nothing found".

Collections carry display name, description, Apple `calendar-color`,
components (`VEVENT` → event, `VTODO` → task; all when the server does
not say; journal-only calendars are skipped), read-only (no
`write` / `write-content` / `bind` / `all` privilege), `getctag`, sync
token and `sync-collection` support (`supported-report-set` or a token).
`DavCollection::to_discovered()` fills the contract's
`DiscoveredCollection`.

### Sync

`sync_collection(client, url, kind, &CollectionState, SyncOptions)`:

1. With `sync-collection` (default): from the stored token (none = the
   initial sync), following truncated answers (`507` on the collection)
   with the new token, up to `max_pages`; a `403` / `409` with
   `DAV:valid-sync-token` restarts with an empty token
   (`token_reset = true`): members not listed any more are reported
   removed, members with an unchanged ETag are not fetched again.
2. Servers that refuse the report (`403`, `400`, `405`, `415`, `422`,
   `501`) fall back to the ctag: unchanged → nothing to do; otherwise a
   `PROPFIND depth 1` ETag listing compared with the stored ETags.
3. Changed members come with `calendar-multiget` / `addressbook-multiget`;
   members the server reports missing in the multiget are treated as
   removed.

`CollectionState` (token, ctag, href → ETag) is the core's to store; the
ETag map must be complete for removals to be detected. Hrefs are URL
paths as the server names them (percent-encoded), the key everywhere.

### Writes and conflicts

`write_object` sends `If-Match: <etag>` for updates and
`If-None-Match: *` for new items; `delete_object` sends `If-Match`. A
`412` means someone else changed the item: **the server wins** — the
result is `WriteOutcome::Conflict(ServerVersion::Current(object))` (or
`Deleted`), and the core shows the server's version and keeps the local
one as a conflict copy (`PimItemSync::Conflict`). A stale delete returns
the server's object (`DeleteOutcome::Conflict`); an already deleted item
is `AlreadyGone`. When a server sends no `ETag` after `PUT`, the item is
read back (servers may rewrite stored data, RFC 4791 §5.3.4).
`member_url` builds `<uid>.ics|.vcf` names with every byte outside
`A-Z a-z 0-9 - _ . ~ @` percent-encoded, so a UID cannot escape the
collection.

### Mock server (`nail-testkit-net::MockDavServer`)

On axum, bound to 127.0.0.1, optionally TLS (an axum `Listener` over
`tokio-rustls` with the testkit CA): one user (Basic and / or bearer),
`/.well-known/` redirects, principal and home sets, default collections
(personal, tasks, read-only holidays, contacts), PROPFIND, all five
REPORTs (sync tokens with history, tombstones, truncation, forgotten
history), conditional PUT / DELETE with content-type checks, MKCALENDAR,
extended MKCOL, PROPPATCH; test hooks to change data as another client,
read it back, inject failures and inspect requests. Its `time-range`
filter compares UTC-normalised `DTSTART` / `DTEND` / `DUE` and always
matches recurring objects (a mock, not a recurrence engine). It keeps its
own copy of the XML tree so it does not depend on the client it tests.

### Interop (Radicale)

`scripts/interop`: `radicale.config` + `radicale.users`
(`ada@example.org` / `nail-interop`, plain htpasswd, test data),
`start-servers.sh` starts `tomsquest/docker-radicale` on 5232 over TLS
with the `gen-certs.sh` certificate (`NAIL_INTEROP_RADICALE=0` skips it),
and `tests/dav.rs` runs discovery, MKCALENDAR / MKCOL, PUT, time-range
query, sync after another client's change, a stale write (conflict),
delete + sync removal, an unknown sync token, address book query /
multiget / both sync paths, and a refused password — for every server in
`NAIL_INTEROP_DAV` (`radicale=https://localhost:5232/`), and always
against the mock over TLS. Verified locally against Radicale 3.8.1 (pip
install in a scratch venv, bound to 127.0.0.1); Radicale is a test server
only (GPL-3.0, run as a separate process, never linked or shipped).

## Consequences

- WP75 builds the sync engine on `discover`, `list_collections`,
  `sync_collection`, `write_object` / `delete_object`, `mkcalendar` /
  `mkaddressbook` / `proppatch`, and maps `DavError` into
  `EngineError` / `PimSourceState` (`AuthFailed` → `auth-error`,
  retryable → `offline`).
- The CI job "interop" needs `NAIL_INTEROP_DAV=radicale=https://localhost:5232/`
  (integrator-owned workflow).
- Not in M3a: scheduling (RFC 6638, WP83), WebDAV-Sync depth infinity,
  `calendar-query` expansion on the server (`<C:expand>`), DNS TXT paths,
  quota properties, Digest authentication.
