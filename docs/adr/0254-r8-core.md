# 0254 — R8 core: rules on a whole list, programs' tasks and events, backlog fixes

Status: accepted (2026-11-24)

## Context

ADR 0251 fixed the shapes of R8 and left the core's behaviour to this
package: free time within working hours (implemented by the contract, tested
here), `RunRules` on a whole list, task reminders from agents and plug-ins,
the MCP tool `create_event_from_text`, and ten backlog rows of the core
(feeds, reminders after a time-zone change, `RDATE` periods, failure
logging, Sieve, server search, the unified list order, the junk classifier,
rule text issues). This ADR records how they work and the choices made where
the brief left room.

## Decision

### Free time

`within_hours` (contract) is pinned by a table over New York, Tokyo, Kolkata
(half an hour off UTC), the March gap in New York, the October repeated hour
in Berlin, Sydney (southern summer time) and Lord Howe (a 30-minute change).

### Rules on a whole list

- `RunRules` with `list` resolves the list like a large mail action (ADR
  0235/0236): the rows as the list pages them, a conversation row = its
  messages in the listed folder (the "listed" reach), minus the `except`
  rows, only messages stored at `as_of` (without a mark: the store's mark
  now). One shared resolver (`mail_actions.rs` `resolve_list`) serves mail
  actions and rule runs.
- A list run excludes `message_ids` and `folder_id` (`invalid_request`).
  Each rule is one `RuleRun` with a `messages` target (the count) and one
  undo. Every rule run (also on picked messages or a folder) now loads and
  evaluates its messages in parts of `RUN_PART_MESSAGES` (500), so a list of
  tens of thousands never holds every message's text at once. A part that
  cannot be loaded ends the run as failed; what it did so far stays
  recorded and undoable. Remote sessions need a full grant (contract).

### Programs: task reminders and events from a sentence

- `upsert_task` and the plug-in task writes (`reminders`, camel case
  `minutesBefore` / `at` for plug-ins, unknown fields refused) replace a
  task's alarms with `TaskReminderArg::to_alarm`; at most
  `MAX_TASK_REMINDERS`; `minutes_before` needs a due (or start) time;
  `[]` removes them. The confirmation and the audit log show the count.
- `create_event_from_text` (policy kind `calendar`, `calendar` scope, no
  invitations) asks the core's `ParseEventText` in the agent's `tz`, else the
  calendar preferences' zone, else the computer's (`McpData::local_zone`, the
  core's `local_zone_name`, which honours `NAIL_TZ`). A sentence without a
  start is refused; an empty title falls back to the sentence. The calendar
  is the named one, else the first writable one the grant reaches (the same
  rule as `create_event`; the MCP has no "preferred" calendar). `dry_run`
  answers the event as JSON and runs nothing (audit detail "dry run").

### Backlog fixes

- **Feed subscriptions.** Where only permanent redirects (`301`, `308`) led,
  the feed's new URL is kept in the calendar's sync state (`href`) and
  fetched from then on; a temporary redirect anywhere in the chain keeps the
  old URL. The login still goes only to the configured URL's origin. A
  changed URL in `accounts.kdl` forgets the moved one. The refresh interval
  a feed asks for is kept in the app setting `pim.feed-refresh.<source>`,
  so an unchanged feed (`304`) and the first pass after a restart follow it.
- **Reminders after a time-zone change.** The reminder task compares the
  local zone's name on every wake (at most `snooze_poll` apart: the portable
  way) and replans when it changed. On Windows a watcher thread waits for
  change notifications of the registry key `TimeZoneInformation` under
  `HKLM\SYSTEM\CurrentControlSet\Control` and wakes the task at once; it
  stops with the task.
  The registry-notification helpers are shared with the appearance watcher
  (`registry_watch.rs`).
- **`RDATE;VALUE=PERIOD`.** `Recurrence.periods` (`RecurrencePeriod {start,
  end}`, the start also in `dates`; left out when empty) keeps a period's
  end, read from `start/end` or `start/duration`. Expansion ends such an
  occurrence at its own end (and looks back far enough for long periods);
  splitting, deleting an occurrence and moving the series keep the periods
  in step. Unchanged items are written back byte for byte; changed ones get
  one `RDATE;VALUE=PERIOD` property per period (date periods are written as
  dates, RFC 5545 has no date periods).
- **Mass failure logging.** A replay pass logs one warning with the account,
  the number of failed writes and the first failure's error class, never
  the text; the per-operation lines are debug.
- **Sieve status after a restart.** The last upload's digest and rule
  placements are also kept in the app setting `sieve.uploaded.<account>`
  (`null` once they no longer describe the server), so the status reads
  `in-sync` right after a restart. The start-up upload still runs (the
  in-memory state decides uploads).
- **Sieve details.** `include :personal` names get the `${` escape under
  `variables` (and are read back without it); a case-insensitive regular
  expression with non-ASCII text has its own reason,
  `sieve-reason-regex-case`.
- **Inexact server search hits.** When the server key is inexact and the
  query has `has:attachment` / `filename:` terms, the server hits' bodies are
  fetched (and kept, as when a message is opened) and
  `nail_search::imap::may_match` drops the hits whose attachments rule the
  query out (three-valued: other terms are the server's and never rule a
  hit out; a file name matches when it contains the text). Storing a fetched
  body now also stores whether it really has attachments (a header block
  could only guess).
- **Unified list order.** In a list over several accounts a thread is also
  ordered by the user's replies from every listed account's Sent folders:
  `SENT_JOIN_PAGE_SQL` reads each joining Sent folder's newest rows of listed
  threads (index range on `thread_activity_order`), merged like the members'
  pages. The pages equal the grouping query for unified scopes (randomised
  test).
- **Junk classifier.** Headers and text are NFKC-normalised before
  tokenising (training data of look-alike forms counts anew). Unsure
  verdicts are stored as unsure (`JunkVerdict.unsure`, schema v26 column
  `junk_verdicts.unsure`). `JunkSettings.ham_cutoff` (default 20, left out of
  JSON when default) is a validated setting below the threshold
  (`JunkIssue::HamCutoff`, `junk-issue-ham-cutoff`); `ClassifierParams` no
  longer carries it.
- **Rule text issues.** `nail_rules::validate_draft` leaves out the blank
  name and values (tag, recipient, reply template, folder path) the draft
  read already reported at their position, so each gap is reported once.

## Consequences

- Agents and plug-ins can set task reminders and create events from a
  sentence; "Run rules on selected" after select all runs on the whole list
  once the UI sends `list`.
- Schema v26; the TypeScript contract gains `JunkVerdict.unsure?`,
  `JunkSettings.ham_cutoff?`, `Recurrence.periods?`, `RecurrencePeriod` and
  `JunkIssue` `ham-cutoff`.
- The plug-in SDK types (`PluginTaskInput` / `PluginTaskChanges`) and the
  settings UI for `ham_cutoff` and unsure verdicts are left to the packages
  that own them.
