# ADR 0088 (WP111): Simple MAPI provider — NailMapi.dll

Status: accepted · 2026-10-02 · M4b WP111 (the integrator renumbers)

## Context

Plan M4b WP111 and design "Windows installer & distribution" → "Simple
MAPI provider": a small Rust DLL that makes Nail the system's Simple MAPI
client, so "Send to → Mail recipient", Office's "Send as attachment" and
any other `MAPISendMail` caller open Nail's composer with the files
attached. ADR 0087 fixed the contract (`nail_api::mapi`: message type,
result codes, pipe name and frames, registry names, DLL paths) and that
the core never sends for a program. This ADR records how the DLL is built.

The DLL runs inside foreign processes (Explorer, Word, 32-bit Office,
anything): it must not crash them, leak handles into them, keep threads or
state in them, or trust any pointer they pass.

## Decisions

### Transport: the per-user named pipe, not the loopback endpoint

The plan allowed either a named pipe with an ACL for the current user or
the loopback endpoint with a per-install token. We use the pipe
`\\.\pipe\nail-mapi-<user SID>` of ADR 0087:

- No sockets at all (the no-non-loopback-sockets rule holds trivially), no
  token file to read from the caller's process, no port discovery.
- Windows enforces who may connect (the shell's DACL grants only the
  user; `PIPE_REJECT_REMOTE_CLIENTS`).
- The client opens it with `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`
  (the server may identify, not impersonate, the caller) and checks the
  **server** before sending anything: `GetNamedPipeServerProcessId` → that
  process's token user SID must equal ours, otherwise
  `MAPI_E_ACCESS_DENIED`. This defeats another user squatting the name
  before Nail starts.
- I/O is overlapped with deadlines (`MAPI_CONNECT_TIMEOUT_MS` = 30 s after
  starting Nail, `MAPI_RESPONSE_TIMEOUT_MS` = 120 s for the answer;
  `CancelIoEx` on expiry), so a hung app cannot hang the caller forever.
- `AllowSetForegroundWindow(server pid)` before sending: the caller owns
  the foreground and lets Nail bring its composer to the front.

The pipe server is the shell's (WP113). It must create the pipe as
`nail_mapi::windows::server::FakeAppPipe` does: `PIPE_ACCESS_DUPLEX |
FILE_FLAG_FIRST_PIPE_INSTANCE`, byte mode, `PIPE_REJECT_REMOTE_CLIENTS`,
SDDL `D:P(A;;GA;;;<user SID>)`; one frame in (`MapiPipeRequest`), one frame
out (`MapiPipeResponse`), then flush and close.

### Starting Nail

When the pipe does not exist the DLL starts the app once and polls for the
pipe: `<install>\Nail.exe` derived from the DLL's own path
(`app_exe_from_dll`: the DLL lives in `mapi\<arch>\`), else
`InstallDir` from `HKCU`, then `HKLM` (64-bit view)
`Software\Nail\Install`. It uses `CreateProcessW` with
`bInheritHandles = FALSE` (not `std::process::Command`, which inherits
handles for stdio) so none of the caller's handles leak into Nail.

Tests set `NAIL_MAPI_PIPE` (contract) and, only together with it,
`NAIL_MAPI_APP` (this crate) to the program to start; with a test pipe the
DLL never falls back to an installed Nail.

### Attachments are copied by the DLL

Programs delete their temporary files as soon as `MAPISendMail` returns,
and some pass files the app could not reach the same way (relative paths,
the caller's working directory). The core already reads every file before
answering (ADR 0087); the DLL additionally:

1. resolves relative paths against the caller's working directory,
2. refuses missing / unreadable / directory paths and files over 25 MiB
   (the composer's limit) before copying anything,
3. copies each file to `%TEMP%\nail-mapi\<pid>-<time>-<n>\<i>\<safe name>`
   (one sub-folder per file, reserved characters and device names made
   safe, the original name kept in `file_name`),
4. sends the copies' paths and removes the folder once the app answered.

Folders left by a killed process are swept by later calls after 24 h.

### The exports

| Function | Behaviour |
| --- | --- |
| `MAPISendMail` (ANSI, `CP_ACP`), `MAPISendMailW` (UTF-16) | decode → checks → copy → pipe → the app's `MapiResult` |
| `MAPISendDocuments` | the delimited files as a message without recipients, with UI |
| `MAPILogon` / `MAPILogoff` | succeed; session handle `1` (no profiles, no passwords) |
| `MAPIResolveName` | a name that is an address (`SMTP:` / `<>` allowed) resolves to itself (`MAPI_TO`, `SMTP:addr`); anything else `MAPI_E_UNKNOWN_RECIPIENT` |
| `MAPIFreeBuffer` | frees buffers from `MAPIResolveName` (tracked); null succeeds; any other pointer is refused with `MAPI_E_FAILURE` and never freed |
| `MAPIFindNext`, `MAPIReadMail`, `MAPISaveMail`, `MAPIDeleteMail`, `MAPIAddress`, `MAPIDetails` | `MAPI_E_NOT_SUPPORTED` (Nail's store and address book are not exposed over Simple MAPI) |

- Signatures and structures are windows-sys' `MAPI.h` bindings
  (`MapiMessage(W)`, `MapiRecipDesc(W)`, `MapiFileDesc(W)`); every export is
  coerced at compile time to its `LPMAPI*` type, so a wrong parameter list
  or calling convention does not build.
- **Robustness**: every export body runs in `catch_unwind` (a panic would
  abort the caller; it becomes `MAPI_E_FAILURE`). Every pointer is checked
  with `VirtualQuery` (committed, readable / writable, not a guard page)
  before it is read or written, reads are unaligned-safe, strings are
  scanned page by page up to a limit (subject / body 8 MiB, other fields
  32 Ki units), counts are checked against the contract's limits before an
  array is touched. A race with another thread freeing the memory is not
  preventable without SEH, which Rust lacks; this is the accepted residual.
- No `DllMain`, no threads, no globals except the `MAPIResolveName`
  buffer table.
- `MAPI_ORIG` recipients are dropped, unknown classes are
  `MAPI_E_BAD_RECIPTYPE`, empty strings count as absent; requests without
  `MAPI_DIALOG` still open the composer (ADR 0087).

### Architectures

- x64 and x86 are built and tested locally (the x86 tests run under WOW64:
  `cargo test -p nail-mapi --target i686-pc-windows-msvc`).
- **x86 export names**: rustc's export list already maps the stdcall
  symbols to plain names (`MAPISendMail = _MAPISendMail@20`, checked with
  `dumpbin /exports`), so no `.def` file is needed — a `/EXPORT` alias
  (tried) only produced LNK4197 warnings. `tests/dll.rs` resolves every
  name with `GetProcAddress`, and `nail-mapi-harness exports --dll <path>`
  does the same for a built artifact in CI.
- ARM64 compiles (`cargo check` / `clippy --target aarch64-pc-windows-msvc`)
  but links only with the MSVC ARM64 build tools, which are not installed
  locally; CI builds it.
- ARM64 Windows runs x64 programs emulated, and they read the same 64-bit
  registry view as native ARM64 programs, which points at the ARM64 DLL.
  An emulated x64 program therefore cannot load it. The remedy is an
  ARM64X DLL (ARM64 + ARM64EC in one file); follow-up, not M4b.

### Registration

`nail_mapi::registration` produces the values; the installers (WP112)
write them, nothing in this crate writes the registry:

- `HKLM\Software\Clients\Mail\Nail` in the **64-bit view**: (default) =
  `Nail`, `DLLPath` = `DLLPathEx` = `<install>\mapi\<x64|arm64>\NailMapi.dll`.
- The same key in the **32-bit view** (`Software\WOW6432Node\…`):
  `<install>\mapi\x86\NailMapi.dll` (32-bit Office reads this one).
- The default client: `Software\Clients\Mail` (default) = `Nail`, `HKCU`
  for a user or `HKLM` for the machine — set only by the user's choice or
  managed deployments (`default_client_entry`).
- `to_reg_file` renders the values as a `.reg` file
  (`nail-mapi-harness registry <dir> --os x64`) for the installers' tests.

Which values the Windows MAPI stub reads (`DLLPathEx` before `DLLPath`,
per view, `HKCU` default before `HKLM`) is from memory of Microsoft's
"Mail client registration" documentation; it could not be confirmed
offline here. WP112's install smoke test on `windows-latest` confirms it
end to end (`MAPISendMailW` through `mapi32.dll`'s stub).

## Consequences

- Any program using Simple MAPI reaches Nail's composer; nothing is sent
  without the user pressing Send.
- The pipe server (WP113) must match the reference server; the integrator
  wires it to `Service::submit_mapi` (WP115).
- CI builds `nail-mapi` for `i686-pc-windows-msvc` and
  `aarch64-pc-windows-msvc` (WP112) and runs the x86 tests.
- Emulated x64 programs on ARM64 Windows need the ARM64X follow-up.
- Callers inside AppContainers / low integrity (rare for Simple MAPI) cannot
  open the medium-integrity pipe and get `MAPI_E_FAILURE`.
