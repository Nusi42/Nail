# ADR 0106: Visual-regression harness and review page

Status: accepted · 2026-10-03 · M5a WP154

## Context

Plan section 10, WP154: a visual-regression harness for the five built-in
themes × two densities (Playwright screenshots of the main window, composer,
settings, calendar, menus and dialogs) with baselines and a review page.
Contract: ADR 0102 (`ListThemes` / `SetTheme` / `SetThemePreferences`,
`data-nail-density`). WP154 owns `e2e/visual/` and `scripts/visual-review/`;
npm scripts, the CI job and doc changes elsewhere are requests to WP155.
While WP154 was built the core answered the appearance requests with
`unsupported` / `m5a-not-ready` (WP152 in parallel), and the new look
(WP151 / WP153) had not landed, so baselines are generated by the
integrator afterwards.

## Decisions

- **Own Playwright project** (`e2e/visual/playwright.visual.config.ts`,
  tests `*.visual.ts`), not part of `npm run e2e`, like `e2e/perf/`. Runner
  `e2e/visual/run-visual.mjs` (Playwright, then the review page; exit code
  = Playwright's). Baselines are written only on request
  (`updateSnapshots: "none"`; `--update` = `--update-snapshots=changed`, so
  unchanged baselines are never rewritten).
- **Data-driven theme list.** The config asks a throw-away
  `nail serve --seed demo-multi` for `ListThemes` while tests are collected
  (synchronously, `lib/probe-themes.mjs`) and hands the answer to the
  workers through the environment. Matrix (`lib/matrix.ts`): the five
  built-ins of the proposal in gallery order, then any further built-in the
  core lists, each × comfortable / compact. The expected five are always
  declared, so a theme the core does not list, lists with a `problem`, or
  cannot list at all becomes a *skipped* test with that reason (printed by
  the runner, listed on the review page) instead of disappearing. User
  themes are never captured. Each worker checks `ListThemes` again on its
  own server before switching.
- **Isolation.** Themes are global server state, so every worker runs its
  own `nail serve --seed demo-multi` (free port, temporary directories;
  `e2e/support/nail.ts` `startNail`) and its variants one after another.
  Default 2 workers (shared machine; `NAIL_VISUAL_WORKERS`).
- **Selection.** `SetTheme <id>`, then `SetThemePreferences` with Follow
  Windows off, the user's light / dark pair unchanged, the variant's density
  and no overrides (baselines show the themes as shipped). The core's
  answer must report the theme as active and the density; after the page
  load the root's `data-nail-density` must match (absent = comfortable), so
  a capture is never mislabelled.
- **Determinism.** Every screen starts from a fresh page load. Fixed clock
  through `page.clock.setFixedTime` before the load (the app reads "today"
  once): `2026-09-30T10:00Z` (after the demo mail's fixed dates); the
  calendar `2026-08-12T10:00Z`, a week before anything `demo-multi` derives
  from the real date (its feeds, meetings and the weekly "Team sync" start
  at the real today), with three fixed events put on the mock CalDAV server
  (`dav-put`, then `SyncPimSources` until `ListEventInstances` has them).
  Time zone UTC, locale en-US, colour scheme light, reduced motion, forced
  colours off, contrast no-preference, viewport 1280 × 800 at device scale 1.
  Before capturing: the demo mail is listed, no account is `connecting`,
  `document.fonts.ready`, the pointer is parked in the bottom-right corner;
  screenshots with animations disabled and the caret hidden are repeated
  until two consecutive ones are byte-identical (at most 8).
- **Screens** (`screens.ts`): `main` (message open), `composer` (filled
  To / Subject / body), `settings`, `calendar` (week view), `menu` (message
  context menu), `dialog` (Move to…). Windows are found by layout window
  name, controls by role and name; M5b changes only these `open` functions.
- **Comparison.** `expect.soft(png).toMatchSnapshot([variant, screen.png])`
  with `maxDiffPixelRatio` 0.002 and `threshold` 0.15
  (`NAIL_VISUAL_MAX_DIFF_RATIO`, `NAIL_VISUAL_THRESHOLD`). Baselines:
  `e2e/visual/baselines/<platform>/<theme>-<density>/<screen>.png` — per
  platform because fonts differ; Windows (`win32`) is the reference used by
  CI and the integrator. `NAIL_VISUAL_BASELINES` points elsewhere (the
  self-test). A screen that fails to open is recorded as `error` and the
  remaining screens are still captured.
- **Manifest and review page.** Each screen writes one JSON record (variant,
  theme, density, screen, status `passed` / `changed` / `new` / `captured`
  / `skipped` / `error`, absolute image paths, message) into
  `<build dir>/visual/manifest/` (one file per record, so workers never
  collide; cleared by the global setup). `scripts/visual-review/generate.mjs`
  turns it into one static page (`<build dir>/visual/review/index.html`)
  with baseline / actual / difference side by side, status filters, skipped
  variants with reasons and baselines no captured screen uses; images are
  copied next to it so the folder is a complete CI artifact; `summary.json`
  for tools. No server, no port.
- **Self-checks.** `harness.visual.ts` captures every screen twice from fresh
  page loads in the server's own theme and fails when the captures differ
  beyond the tolerance (a dependency-free PNG decoder, `lib/png.ts`, counts
  differing pixels and reports their bounding box) — this caught a few
  anti-aliased pixels of a native `select` that differ between loads, which
  is why the self-check uses the comparison tolerance rather than byte
  equality. `selftest.mjs` runs the harness end to end with temporary
  baselines and the pseudo theme `current` (the server's own theme, never
  in the default matrix): no baselines → `new` and failure; `--update` →
  written; again → `passed`; one baseline replaced → `changed` with a diff
  image on the review page.
- **Output** only in the build directory (`NAIL_BUILD_DIR` /
  `%LOCALAPPDATA%\nail-build`, `NAIL_VISUAL_RESULTS`); only reviewed
  baselines are committed.

## Consequences

- Until WP152 lands, all ten variants are skipped with the `m5a-not-ready`
  reason and only the self-check captures; once the core switches themes the
  variants run and fail as `new` until the integrator generates and reviews
  the baselines (`npm run visual:update`).
- The CI job starts non-blocking (`continue-on-error`) and becomes blocking
  once the baselines are reviewed; the review page is uploaded as an
  artifact either way.
- Baselines must be regenerated whenever the look or a screen's content
  changes on purpose (M5b shell changes in particular).
